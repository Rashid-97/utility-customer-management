# Domain

This document is the source of truth for Customer Management language and business rules.

## Language

- **Applicant** — a person submitting an application. It is not a persisted entity.
- **Subscriber** — a person recognized by the utility provider and the only Aggregate Root.
- **SubscriberAccount** — an Entity inside Subscriber that represents utility service at one address.
- **ServiceAddressId** — a reference to address data owned outside Customer Management.
- **IdentityDocument** — verified identity data received from the external Identity boundary.
- **SubscriberCode** — a business identifier built from CityCode, StreetCode, BuildingCode, and ApartmentCode.
- **Billing** — an external bounded context consulted for outstanding debt.
- **GIS** — an external bounded context used here as the source of address validity and serviceability.

## Aggregate boundary

`Subscriber` owns all account state changes. A `SubscriberAccount` has identity, but it is not an Aggregate Root and has no separate repository.

```text
Subscriber (Aggregate Root)
└── SubscriberAccount (Entity)
```

A Subscriber and the first account are created in the same transaction. Adding or terminating an account always goes through Subscriber.

## Registration

Registration follows this order:

1. Verify the submitted identity document through `IdentityVerificationPort`.
2. Use the verified `(document_type, document_number)` pair to find an existing Subscriber.
3. Verify the service address through `AddressVerificationPort`.
4. Check that the applicant is at least 18 on the application date.
5. Reject the request if any Subscriber already has an active account at that address.
6. For an existing Subscriber, check all existing accounts for outstanding debt.
7. Create the Subscriber when needed, add the account, and commit once.

Identity data is authoritative. The API does not accept first name, last name, date of birth, or citizenship as independent registration fields.

Finding an existing Subscriber is not an error. The same registration use case adds a new account when all rules pass.

## Account rules

- A Subscriber may own several accounts.
- Each account belongs to exactly one Subscriber.
- Only one `ACTIVE` account may exist for a ServiceAddressId across all Subscribers.
- An additional account requires all existing accounts of that Subscriber to be debt-free.
- Termination requires the target account to be debt-free.
- Termination changes the state to `TERMINATED`; it does not delete the account.
- A terminated account cannot be terminated again.
- SubscriberCode is unique and remains attached to a terminated account.

Address verification and address uniqueness are separate rules. GIS answers whether an address is valid and serviceable. Customer Management checks whether an active account already uses it.

## Value objects and identity

The Domain uses immutable value objects:

- `IdentityDocument`
- `ServiceAddressId`
- `SubscriberCode`
- `CityCode`
- `StreetCode`
- `BuildingCode`
- `ApartmentCode`

There is no shared ValueObject base class. `SubscriberCode.create(...)` receives the four typed code components and concatenates them in city, street, building, apartment order.

Subscriber and SubscriberAccount use typed `Id[T]` values backed by UUIDs. UUIDs are generated by the server.

## Application verification

`ApplicationVerificationPolicy` decides whether verified facts satisfy the application rules. It receives identity status, address status, date of birth, and application date. It does not call external services.

Handlers obtain the external facts through ports and pass them to the policy.

## Domain events

Successful state changes record:

- `SubscriberCreated`
- `SubscriberAccountCreated`
- `SubscriberAccountTerminated`

Events contain an event ID, occurrence time, and aggregate ID. They are kept in memory and cleared only after a successful commit. No dispatcher, broker, or durable delivery is implemented.

`ApplicationSubmitted` and `ApplicationVerified` belong to the discovery-level business flow; they are not tactical event classes in this implementation.

## External ownership

Customer Management stores only the references and facts needed by its own model. It does not implement Identity, GIS, ServiceAddress, or Billing bounded contexts.

The current adapters are deterministic mocks. Their contracts allow real integrations to replace them without changing Domain code.
